Redesign Approach

How aggressively should we restructure? All options adopt the Stitch visual language with PRD colors.

A

Reskin — Visual Layer Only

Keep all existing component structure and logic. Update design-tokens.ts with new surface hierarchy, glassmorphism values, and Stitch-inspired spacing. Restyle existing components (StationCard, PlayerScreen, etc.) in-place. Add new screens as minimal implementations.

Pros

  • Lowest risk — existing logic untouched
  • Fastest to implement
  • Working app stays working throughout

Cons

  • New screens (Queue, Onboarding, Settings) still need full builds
  • Existing component structure may fight Stitch layouts
  • Tab navigation requires navigation architecture changes regardless
B

Progressive Rebuild — Screen by Screen (Recommended)

Rebuild the design system tokens first. Then rebuild each screen one at a time, preserving service/engine logic but rewriting the UI layer. Shared components (tab bar, glass panels, headers) built as a foundation first. Each screen is a self-contained milestone.

Pros

  • Each screen is a testable milestone
  • Shared components built once, used everywhere
  • Clean break from old layout patterns
  • Can ship incrementally — each screen works independently

Cons

  • More work than reskin
  • Temporary inconsistency between rebuilt and unrebuilt screens
Build Order:
  1. Design tokens + shared components (tab bar, glass panels, header)
  2. Bottom Tab Navigation (unlocks all screens)
  3. Now Playing / Broadcast (core experience)
  4. Cleo Speaking overlay (enhances core)
  5. HomeScreen redesign (entry point)
  6. Onboarding (new flow)
  7. Session Arc / Queue (new screen)
  8. Profile & Settings (new screen)
C

Full Rewrite — New UI from Scratch

Start the UI layer fresh. New navigation structure, new component library, new screen implementations. Keep all service code (MusicKit, Gemini, ElevenLabs, audio coordination) but rebuild every visual component.

Pros

  • Cleanest result — no legacy compromises
  • Can optimize component architecture from the start

Cons

  • Highest risk — breaks everything temporarily
  • Longest timeline
  • Existing working features go dark during rebuild
  • Over-engineering for what's needed
