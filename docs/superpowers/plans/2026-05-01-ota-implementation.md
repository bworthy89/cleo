# OTA Implementation Plan

> **For agentic workers:** Execute task-by-task with `superpowers:executing-plans`. Several tasks have human gates (Sentry web UI, EAS build cycles, TestFlight install) that block automated execution; do not skip these by stubbing.

**Goal:** Wire `expo-updates` so JS-only changes ship to TestFlight builds in ~2 min via `eas update --branch production` instead of a 30-60 min EAS build cycle. Bundle Sentry source-map upload so post-OTA crashes remain debuggable. Use fingerprint runtime policy so OTAs auto-scope to compatible binaries (no manual `runtimeVersion` bumps).

**Architecture:** Five surgical pieces wired together: (1) `expo-updates` installed + configured with fingerprint runtime policy, (2) single `production` channel — no preview-channel theater, (3) Sentry source-map upload enabled via auth token + EAS secrets + flipped flag, (4) AppState foreground hook that checks for updates and reloads only when no broadcast is playing, (5) npm scripts + rollback playbook documented.

**Tech Stack:** Expo SDK 55, `expo-updates`, `@sentry/react-native ~7.11.0`, EAS CLI, AppState (React Native).

**Spec:** [`docs/superpowers/specs/2026-05-01-dev-pipeline-design.md`](../specs/2026-05-01-dev-pipeline-design.md) — Tier 1 #1.

## Phase ordering rationale

The order below is dictated by hard dependencies, not preference:

1. **Code changes first** so the build cycle picks them up. Cheap, reversible.
2. **Sentry web UI before EAS secrets** — secrets can't be created without the auth token.
3. **EAS secrets before EAS build** — the build fails the source-map upload step without them.
4. **Local prebuild before EAS build** — EAS no longer runs prebuild (CLAUDE.md), so the iOS native files must be regenerated locally and committed.
5. **EAS build + TestFlight install before OTA push** — there has to be a binary in the wild to receive the update.
6. **Two OTA pushes before rollback dry-run** — `eas update:republish` needs a previous group ID to republish.
7. **CLAUDE.md updates last** — only after everything works, so the docs reflect reality.

### Step 1.3 — Configure update URL in `app.json`

- [ ] Add to `app.json`'s `expo` block:
  ```json
  "updates": {
    "url": "https://u.expo.dev/65e6f716-8b20-415c-9827-cfcef3e2c8ae",
    "enabled": true,
    "fallbackToCacheTimeout": 0,
    "checkAutomatically": "ON_LOAD"

  ```
  The URL pattern is `https://u.expo.dev/<projectId>`; project ID lifted from `expo.extra.eas.projectId`. `fallbackToCacheTimeout: 0` means cold-start launches don't block on the network update check; the foreground hook (Task 4) handles the active-session check.

**Verify:** `node -e "console.log(require('./app.json').expo.updates.url)"` echoes the URL.

## Task 2: Fingerprint runtime versioning

**Files:** `app.json`

### Step 2.1 — Replace static `runtimeVersion`

- [ ] In `app.json`, replace `"runtimeVersion": "1.1.2"` with:
  ```json
  "runtimeVersion": {
    "policy": "fingerprint"
  }
  ```
  Expo's CLI will compute the fingerprint at build time from native deps + plist + plugin config. Native changes auto-bump the runtime; JS-only changes leave it unchanged.

**Verify:** `npx expo-updates fingerprint:generate` (or `npx @expo/fingerprint` if the former isn't available in SDK 55) prints a hash without errors.

**Migration note:** The currently-shipped TestFlight builds (build 63 and earlier) have `runtimeVersion: "1.1.2"` baked in. The first OTA push under fingerprint policy will *not* reach those builds — they're scoped to the `1.1.2` literal. This is correct behavior (we don't want a new-fingerprint OTA hitting a 1.1.2 binary), but means the loop only goes live after the next EAS build (Task 6).

## Task 8a: Build-bump script (atomic native-build prep)

> **Why this is a hard prereq for Task 9, not a nice-to-have:** bare workflow forces literal `runtimeVersion` in app.json + `EXUpdatesRuntimeVersion` in `Expo.plist` (no auto-bump policies allowed; see Task 7 amendment). Without an atomic bump script, every native build needs four hand-edits in lockstep — and forgetting the runtime-version side means a future OTA push lands on a binary it doesn't match and crashes every TestFlight installer with the older build. The whole point of OTA is fast safe updates; manual lockstep across four files defeats that. This script makes the operation atomic.

**Files:**
- New: `scripts/bump-build.mjs` (matches the existing `scripts/generate-icons.mjs` style)
- Modify: `package.json` — add `bump:build` script

### Step 8a.1 — Write the script

- [ ] `scripts/bump-build.mjs` with two modes:

  **Default mode (`npm run bump:build`)**: bumps build number only.
  - Read `ios/ONAY.xcodeproj/project.pbxproj`, find all 4 `CURRENT_PROJECT_VERSION = N;` occurrences, bump to N+1.
  - Read `app.json`, bump `expo.ios.buildNumber` to match.
  - Print: `bumped build to N`.

  **Release mode (`npm run bump:build -- --release patch|minor|major`)**: bumps build number AND version (which bumps runtime version, breaking the OTA chain to old binaries — exactly what you want when adding native deps).
  - Everything default mode does, plus:
  - Read `app.json`, semver-bump `expo.version` (e.g. `1.2.0` → `1.2.1` for patch).
  - Set `app.json`'s `expo.runtimeVersion` to the new version string.
  - Set `ios/ONAY/Supporting/Expo.plist`'s `EXUpdatesRuntimeVersion` to the new version string.
  - Print: `bumped build to N, version to V.V.V (runtime version bumped — old binaries will NOT receive OTAs from this build)`.

- [ ] Validation: refuse to run if any of the four version sources are out of sync at start (means a previous bump was partial). Either fix manually or run with `--force`.

### Step 8a.2 — Register the script

- [ ] Add to root `package.json`:
  ```json
  "bump:build": "node scripts/bump-build.mjs"
  ```

### Step 8a.3 — Test

- [ ] `git stash` any in-flight changes, run `npm run bump:build`, verify pbxproj + app.json bumped in lockstep, runtime untouched. Then `npm run bump:build -- --release patch`, verify all four bumped. `git restore` the test changes.

### Step 8a.4 — Update DOD checklist (in this plan and in CLAUDE.md when Task 11 lands)

- [ ] Replace the "bump CURRENT_PROJECT_VERSION in pbxproj + app.json buildNumber in lockstep" line in the Native iOS DOD with: "run `npm run bump:build` (default) or `npm run bump:build -- --release patch|minor|major` (when adding native deps)."

## Task 8b: Pre-OTA-push guard

> **Why this is a hard prereq for Task 9:** even with the bump script enforcing atomicity at build time, a forgotten `eas build` between native changes and an OTA push still ships a JS bundle to a binary it doesn't match. The guard catches this at OTA-push time by comparing the working tree's `runtimeVersion` against what the latest TestFlight binary actually shipped with. If they differ, refuse the push.

**Files:**
- New: `scripts/guard-update.mjs`
- Modify: `package.json` — wrap `update:prod` and `update:prod:safe`

### Step 8b.1 — Write the guard

- [ ] `scripts/guard-update.mjs`:
  - Read current `app.json`'s `expo.runtimeVersion` (literal string).
  - Run `eas build:list --platform ios --limit 1 --json --status finished` to get the latest finished production build.
  - Parse its `runtimeVersion` field.
  - If they match → exit 0, allow the push.
  - If they differ → print: `runtime version mismatch: working tree=X, latest TF build=Y. You have native changes since the last build; run npm run bump:build -- --release <bump> + eas build first.` Exit 1.
  - Edge case: no builds yet (empty result) → print warning, allow push.
  - Then `exec` into the actual `eas update --branch production [--rollout-percentage N]` command, forwarding all extra args.

### Step 8b.2 — Wrap update:prod scripts

- [ ] Change `package.json`:
  ```json
  "update:prod": "node scripts/guard-update.mjs --branch production",
  "update:prod:safe": "node scripts/guard-update.mjs --branch production --rollout-percentage 25"
  ```
  Also add a `update:prod:nogard` escape hatch for the rare case the guard is wrong and you really mean to push:
  ```json
  "update:prod:noguard": "eas update --branch production"
  ```

### Step 8b.3 — Test

- [ ] Manually mismatch versions: bump `app.json` runtimeVersion to a higher value than the latest TF build's, run `npm run update:prod`. Should refuse. Restore.
- [ ] With matched versions, run `npm run update:prod -- --message "guard test"`. Should proceed (use a trivial JS change so the OTA itself is harmless).

## Rollback if mid-implementation goes wrong

The risk surface is concentrated in two places:

**Sentry source-map upload breaks the EAS build.** Fix forward by flipping `SENTRY_DISABLE_AUTO_UPLOAD` back to `"true"` in `eas.json`, rebuilding, and debugging the Sentry config separately. OTA can ship without source maps in the interim — it's a debugging regression, not an outage.

**Foreground hook causes a crash.** The hook is wrapped in try/catch and only fires on AppState transitions, so the blast radius is small. If a crash happens, immediately push an OTA that no-ops the hook (`if (false) return; ...`) — Sentry will tell us within minutes via crash reports.

**Fingerprint policy doesn't compute.** Fall back to `"appVersion"` policy; it's a one-line change in `app.json`. Less precise (won't catch a native dep added without a marketing version bump) but functional.

**Bad OTA in production.** Use Task 10's republish playbook. The whole point of building rollback into the loop.

## Out of scope

- **Tester cohort management.** No invite-list logic, no per-tester targeting. Single `production` channel; everyone on TestFlight gets every OTA (modulo `--rollout-percentage`).
- **Per-update analytics dashboard.** Sentry handles crashes; bake/playback metrics are separate.
- **A `staging` channel.** Defer to Phase 3 of the dev pipeline (staging server lands first; staging-channel OTAs become useful once staging-targeting builds exist).
- **Android.** iOS-only for now per the project scope; Android plumbing for `expo-updates` would parallel iOS but is unused.
- **Update bundle splitting / asset optimization.** Default expo-updates behavior is fine; revisit if bundle size becomes a problem (current bundle is small).
